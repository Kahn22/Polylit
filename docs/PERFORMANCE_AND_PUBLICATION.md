## Source of truth and safeguards

- `content/published/registry.json` is the explicit approval list, including stable work IDs and languages. It is not regenerated by content producers. Every approved work must remain present and learner-ready. Unknown works, duplicates, missing works, and language changes block a release before delivery files are touched.
- `content/published/works/<workId>.json` contains the work metadata, exact canonical source and provenance, source checksum, thought units, occurrences, exclusions, notes, readiness, expression occurrences, and references to that work's editorial-review files.
- `content/published/shared/fr.json` and `es.json` hold each language's lemmas, senses, surface forms, prepared vocabulary quizzes, expression identities, and prepared expression quizzes. Permanent IDs and Surface form + Sense mastery keys are unchanged.
- Source packages and browser delivery use neutral fields: `text`, `context`, `choicesTarget`, `choicesGloss`, and `promptTarget`. Language is explicit; country-of-origin metadata remains independent. `src/publication/format.ts` adapts historical French-named authoring fixtures for existing validation and migration tests. Legacy names are not shipped in new delivery packages.
- Historical `content/learning/jaccuse*.json` files remain unmodified regression/migration fixtures. Production no longer reads or writes them. A regression test compares every migrated record against the original snapshot.

To intentionally retire a work, change its registry status to `retired` and provide a nonempty `retirementReason`. Its source package and learner progress remain intact. Rebuild/validate before any separate deployment. Do not remove an approved registry entry as a substitute for retirement.

## Updating an existing work

1. Prepare and review canonical/linguistic content offline using the existing editorial pipeline. Look up existing shared identities and prepared questions before creating any new ones.
2. Import only the approved work, not an aggregate replacement:

   ```bash
   npm run publication:import -- --work wrk_zola_jaccuse --input reviewed-bundle.json --expressions reviewed-expressions.json
   ```

3. If an existing shared definition or question differs, import stops. Review its effect on every referencing work; use `--replace-shared` only when that shared change is intentional. Missing quiz bands or invalid source references still fail validation.
4. The complete candidate is validated in memory, staged, re-read and validated again, then adopted. The previous source directory is retained under `content/.publication-previous-*` for recovery. Temporary/previous directories are ignored by Git and never shipped.
5. Run `npm run check` and `npm run build`. Inspect the result before separately approving preview/publication or updating GitHub Desktop.

The Zola, Spanish, curated-fable, and remaining-work producers now import selected works through the guarded path instead of overwriting the old shared catalog. `content:build` builds delivery only. `content:check` validates sources without changing them.

New works need an explicitly approved registry entry and a reviewed work package before assembling a release. This is intentionally a fail-closed gate, not automatic approval by a producer.

## Page delivery

| Surface | Required content |
| --- | --- |
| Login / language selection | Static HTML, ordinary stylesheet, small navigation/entry scripts; no library fetch |
| Language library | Build-generated book cards and compact embedded index; no duplicate catalog fetch |
| Book View | Small work manifest plus the selected text-only page |
| Learning View | Small work manifest plus the current natural passage, referenced vocabulary, and section expressions |
| Review | Small language quiz index plus self-contained question packages; no reading section required |

Library membership uses compact, deterministic delivery tokens checked for collisions at build time. These are lookup references only: localStorage, encounters, scheduling, and questions continue using the original full mastery keys. Derived indexes compute counts and queues once per state revision, invalidating at the next due time and on shelf/progress changes. Language-specific localStorage keys are unchanged.

The reader, Book View, and question markup are separate code chunks. Heavy editorial schemas are kept out of the browser dependency graph. CSS loads independently of JavaScript. The library layout is generated by the same renderer at build time and in the browser; personal shelves/counts are applied locally, not published.

## Stable releases and caching

- Content-addressed filenames change only when a payload changes. Work manifests and quiz indexes point to those exact files; the embedded language index identifies its release.
- Quiz grouping uses 512 deterministic buckets per language, rather than globally sorted sequential batches. Adding an item does not renumber other buckets. All three prepared bands stay together. Storage grouping does not change ten-question review sessions.
- Build validation finishes before any output writes. Immutable payloads are written first, mutable language entry indexes last. Byte-identical files are not rewritten. Complete-release validation is still performed every build.
- Existing hashed output is retained during incremental builds for open tabs. A clean deployment must retain prior hashed assets if uninterrupted old-tab support is required. If an older asset is unavailable, the Retry action reloads the current release rather than repeatedly requesting the missing file.
- The browser requests versioned assets with `force-cache` and entry indexes with `no-cache`. `_headers` supplies private, immutable cache directives for compatible static hosts. Actual HTTP headers depend on the deployment host; GitHub Pages does not apply this file as a custom-header configuration. No shared caching of learner-specific data is introduced.
- Loader memory is bounded to 64 recent requests. Only active-section linguistic records are held by the UI. Downloads time out after 12 seconds; failed requests are evicted and retryable. Prefetch failures do not reject navigation or change encounters.
- There is no service worker, offline-content guarantee, runtime AI, new database, or account migration.

## Checks and baseline measurements

`npm run check` checks types and the complete test suite, including migration equivalence, catalog protection, language separation, deterministic packaging, progress indexes, native language links, Book View encounter isolation, viewed-unit encounters, quiz delivery, and retry behavior.

`npm run build` also runs `check:performance`, checking every generated content reference and route asset, matching embedded indexes to releases, pre-generated card counts, language isolation, three quiz bands, and compressed size budgets. Budget increases require an intentional code review when the catalog grows.
